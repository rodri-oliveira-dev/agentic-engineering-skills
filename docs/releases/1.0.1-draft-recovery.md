## Failure cause

The original pipeline used `gh release create --draft`, which created a Draft Release and uploaded its assets, but did **not** create the Git ref immediately. A subsequent step executed `gh api repos/.../git/ref/tags/1.0.1`; GitHub returned **HTTP 404**. The step failed before downloaded-asset verification, leaving the valid, attested candidate unpublished.

## Corrective actions

- Regular publication: address Draft Releases by **numeric release ID**, read back all asset bytes through the authenticated Releases API, check uploaded SHA-256 digests and compare original bytes. Only verify the newly created tag after the Draft is published.
- Existing Draft: add a separately authorized, protected [Recover verified release draft](../../.github/workflows/recover-release-draft.yml) workflow. It must validate a numeric release ID, exact release version, original source commit ancestry, digest of all three downloaded assets, original cryptographic signer and SHA, absence of a preexisting tag, and the post-publication tag target. The recovery workflow never rebuilds or overwrites the original assets.
- Preserve the immutable source and the historical 1.0.0 release. The recovery job cannot mark this incident closed until GitHub Actions records a successful run and the published tag is independently verified.

## Recovery inputs

After the corrective PR is merged into main and the `release` Environment protection is confirmed, use the manual recovery action with:

- **Version:** `1.0.1`
- **Release ID:** `455709541`

The recovery job verifies the original 2026-11-23 attestation from source commit `8f6cd2ff748cca8af81dc54a06a426e4d2b0f1d5`. A new commit that fixes the release workflow is permitted as an ancestor extension of main, but does not silently change the original release's source commit.

Do not delete the Draft, retry the regular `Publish release` workflow, or publish manually until recovery has been reviewed. If the recovery checks fail, keep the Draft unpublished and investigate.
