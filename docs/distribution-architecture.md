# Plugin distribution architecture

## Scope and decision

This repository distributes the ten canonical Agent Skills as one plugin named `agentic-engineering`. The plugin is intended for users who want the complete, cohesive software-engineering workflow library through a marketplace. Direct Agent Skills discovery and the existing Claude Code installer remain supported.

The selected model is one plugin containing all ten skills. A single package matches the catalog's release lifecycle, avoids ten manifests and ten independently versioned installation units, and gives users one update operation. The trade-off is that users cannot install a marketplace subset. They can still copy or install individual canonical skills through the existing Agent Skills workflows.

Splitting by responsibility was considered. A possible grouping would separate design and documentation, code quality, debugging and security, data, and delivery. That would reduce installed context for users who need only one domain, but it would introduce overlapping boundaries, more release coordination, and a higher risk of inconsistent versions. Individual plugins would maximize selection while multiplying manifest, marketplace, validation, and support work. The current catalog is small enough that these costs outweigh the benefit. A future split is justified only by measured context or installation costs, separate ownership, or independently evolving compatibility requirements.

## Marketplace and package organization

```text
.
├── .agents/
│   ├── skills/                         # the only canonical skill source
│   └── plugins/marketplace.json        # OpenAI local/repository catalog
├── .github/plugin/marketplace.json     # GitHub Copilot CLI catalog
├── .claude-plugin/marketplace.json     # Claude Code catalog
├── plugins/agentic-engineering/        # generated installable package
│   ├── plugin.json                     # Agent Plugins 1.0 manifest
│   ├── .claude-plugin/plugin.json      # Claude Code compatibility manifest
│   ├── skills/                         # generated byte-for-byte skill tree
│   └── .agentic-engineering-package.json
├── scripts/package_plugins.py
└── tests/test_package_plugins.py
```

All three catalogs point to the same plugin directory. Marketplace files differ only where their hosts require different metadata shapes. The package contains no MCP server, hook, agent, or host-specific skill content.

The Codex catalog includes the host-required installation and authentication timing policy fields. `authentication: ON_INSTALL` is marketplace policy metadata required by the current catalog contract; it does not configure authentication for this skills-only plugin. The package contains no MCP authentication configuration, credentials, registered app mapping, or `extensions.com.openai` block.

## Canonical source and derived artifacts

`.agents/skills/` is the only editable source for `SKILL.md`, `references/`, `scripts/`, and `assets/`. The package `skills/` tree is generated byte for byte from that catalog. It must not be edited directly.

Agent Plugins 1.0 requires portable skills under the fixed package-relative `skills/` directory. Paths outside the plugin root cannot supply that component. Consequently, the package cannot point back to `.agents/skills/`, and symlinks would not be a reliable remote-install mechanism. A generated copy is therefore required for marketplace distribution even though direct Codex and Copilot project discovery can reuse `.agents/skills/` without a copy.

The embedded `.agentic-engineering-package.json` records SHA-256 for every package file except itself. It provides detached integrity verification and identifies the canonical source and generator. The repository check independently reconstructs the entire expected package, including the inventory and marketplace manifests, so an edited inventory cannot make a derived edit canonical.

## Platform compatibility

| Platform | Marketplace manifest | Plugin manifest | Skills location | Compatibility approach |
| --- | --- | --- | --- | --- |
| OpenAI Codex and ChatGPT local plugins | `.agents/plugins/marketplace.json` | Root `plugin.json` | Fixed `skills/` | Native Agent Plugins 1.0 package; no `.codex-plugin/plugin.json` fallback is needed |
| GitHub Copilot CLI | `.github/plugin/marketplace.json` | Root `plugin.json` | Fixed `skills/` | Native Agent Plugins 1.0 package; root manifest takes precedence over legacy manifests |
| Claude Code | `.claude-plugin/marketplace.json` | `.claude-plugin/plugin.json` | Default `skills/` | Thin legacy compatibility manifest over the same generated skill tree |
| Direct Agent Skills | None | None | `.agents/skills/` in this repository | Existing installation and repository discovery remain unchanged |

The root `plugin.json` declares `https://agent-plugins.org/schemas/1.0.0/plugin.schema.json`. Agent Plugins 1.0 defines only skills and MCP servers as portable components and uses fixed `skills/` and `mcp.json` locations. This package has no MCP component, so no empty `mcp.json` is generated.

Legacy plugin formats differ materially. OpenAI's supported Codex compatibility manifest uses `.codex-plugin/plugin.json` and declares component paths. Copilot CLI legacy manifests allow configurable component locations and several manifest paths. Claude Code uses `.claude-plugin/plugin.json`, supports additional Claude-specific component fields, and scans `skills/` by default. New portable packages should not put legacy top-level component fields such as `skills` into the Agent Plugins 1.0 root manifest. The Claude compatibility manifest remains separate because Claude Code's documented native manifest location is still `.claude-plugin/plugin.json`.

The structure follows the useful marketplace pattern in Microsoft's [`dotnet/skills`](https://github.com/dotnet/skills): host catalog files point at plugin subdirectories that contain a `skills/` tree. The reference repository currently carries duplicated host manifests as a compatibility bridge and groups a much larger catalog into domain plugins. This repository instead uses the published Agent Plugins 1.0 root manifest for OpenAI and Copilot, adds only the Claude compatibility manifest, and generates all skill content from the canonical tree.

## Generation, verification, and updates

The generator requires Python 3.11 or newer and otherwise uses only the standard library. No JavaScript, .NET, package manager, network access, or installed agent is required.

Generate all package and marketplace artifacts:

```shell
python scripts/package_plugins.py generate
```

Check that tracked output exactly matches the canonical catalog and generator metadata:

```shell
python scripts/package_plugins.py check
```

Verify a package against its embedded hashes, including after copying or extracting it elsewhere:

```shell
python scripts/package_plugins.py verify --package plugins/agentic-engineering
```

Generation is deterministic: paths are sorted, JSON keys are sorted, UTF-8 and LF are used for generated JSON, no timestamps or machine paths are recorded, and skill file bytes are preserved. Before replacing an existing package, the generator validates its current embedded inventory. It refuses to overwrite missing, extra, or modified derived files. This makes manual edits visible instead of silently discarding them. Marketplace drift is detected by `check` and by the automated test suite.

The update workflow is:

1. edit only `.agents/skills/` or the generator's package metadata;
2. run the canonical validator and tests;
3. run `python scripts/package_plugins.py generate`;
4. run `python scripts/package_plugins.py check` and `verify`;
5. review both the canonical changes and generated diff.

## Versioning strategy

The plugin version follows the repository release version and uses Semantic Versioning. The published initial package is `1.0.0`; adding backward-compatible skills or package capabilities is a minor change, compatible fixes are patch changes, and incompatible skill contracts or package behavior require a major change. Marketplace entries and both plugin manifests are rendered from the single `PLUGIN_VERSION` constant in the generator, preventing host-version drift.

The project release version identifies a release line, the Git tag identifies its repository revision, and the generated marketplace/plugin version tells clients which plugin package they are selecting. They are aligned for `1.0.0` but have different roles. Generated file hashes identify package bytes; they are not a release version and do not replace Git history, tags, release signatures, or archive checksums. Updates remain explicit: change the version when release contents require it, regenerate, validate, and publish only through the repository's release process. Documentation-only changes that do not alter canonical skills or package metadata do not require package regeneration or a plugin-version change. This infrastructure does not create a release, push a branch, or publish a marketplace entry.

## Architectural limitations

- Codex CLI local marketplace discovery and installation were exercised before publication. After publication, Codex CLI `0.171.0-alpha.13` also registered the public GitHub `owner/repo` source and installed version `1.0.0` in an isolated `CODEX_HOME`. The interactive `/plugins` browser and behavioral skill activation remain untested. Copilot CLI and Claude Code were unavailable, so their native validators and marketplace installation remain untested. Offline validators confirm each catalog's identity, metadata, confined relative source, manifest, and exact ten-skill inventory, but structural compatibility is not behavioral evidence.
- The OpenAI catalog uses repository-local source metadata. Public directory submission may require additional publisher, presentation, privacy, review, or signing metadata at publication time.
- Claude Code retains its native `.claude-plugin/plugin.json` compatibility manifest because its current manifest reference documents that location. It contains metadata only and leaves component discovery to the standard `skills/` layout.
- One plugin means marketplace users receive all ten skills. Direct Agent Skills installation remains the subset-installation path.
- SHA-256 detects accidental or reviewable drift; it does not authenticate the publisher or defend against a party that can rewrite both files and hashes.
- The generator deliberately rejects source and package symlinks. This favors reproducible remote installation across operating systems over filesystem-level deduplication.
